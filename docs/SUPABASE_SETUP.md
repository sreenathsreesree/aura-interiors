# AURA Interiors — Supabase Cloud Foundation Setup

This document is split into two halves on purpose:

- **Implemented in code** — everything in this repo that is done and typechecks/builds/lints clean, but has **not** been exercised against a real Supabase project (this development environment has no Supabase credentials).
- **Manual Supabase configuration required** — the steps a developer with real Supabase access must run before any of the above can be tested end-to-end.

Nothing here is faked. Until the manual steps below are completed, AURA runs in **local-only mode**: every existing feature (Clients, Projects, Rooms, BOQ, Quotations, PDF, Canvas, Site Photos, References) works exactly as it did before this milestone, with no sign-in wall and no cloud sync — see "How local-only mode works" below.

## Implemented in code

- `@supabase/supabase-js` client (`src/supabase/client.ts`), gated by `isSupabaseConfigured()`.
- Full Postgres schema + Row Level Security policies (`supabase/migrations/0001_init.sql`).
- Email/password auth: sign up, sign in, sign out, forgot password, reset password, persistent session (`src/supabase/auth.ts`, `src/store/useAuthStore.ts`, `src/features/auth/*`).
- An `AuthGuard` wrapping every existing route, a sync status indicator, and an account menu in the Sidebar / mobile top bar.
- A local-first sync layer: debounced push queue with retry (`src/supabase/sync/syncQueue.ts`), cloud bootstrap on sign-in (`src/supabase/sync/cloudBootstrap.ts`), and a first-login migration flow that offers to sync existing local data to a brand-new cloud workspace (`src/supabase/sync/migrateLocalData.ts`, `src/features/auth/MigrationPrompt.tsx`).
- Site Photos moved to Supabase Storage (private bucket, signed URLs) when signed in; References keep Google Drive files external and store only metadata, exactly as before.
- Canvas documents persist to a `canvas_documents` table as the same JSON already written to `localStorage` — no change to the Canvas data model, coordinate system, or drawing logic.
- Per-account local-storage namespacing (`src/supabase/localNamespace.ts`) so two different cloud accounts signing into the same browser never see each other's cached Canvas/Media data.

**None of this has been run against a live Supabase project.** Typecheck, lint, build, and every existing Playwright regression suite pass with Supabase unconfigured. The steps below are what's needed to actually test the cloud half.

## 1. Create the Supabase project

1. Go to [supabase.com](https://supabase.com) and sign in.
2. **New project** → pick an organization, name it (e.g. `aura-interiors`), set a database password, choose a region close to your users.
3. Wait for provisioning (a couple of minutes).

## 2. Find the project URL and publishable key

In the project dashboard: **Project Settings → Data API**.

- **Project URL** → this is `VITE_SUPABASE_URL`.
- **Project API keys → `anon` `public`** → this is `VITE_SUPABASE_PUBLISHABLE_KEY`.

Do not use the `service_role` key anywhere in this app — it must never reach the browser.

## 3. Set environment variables

Copy `.env.example` to `.env.local` (already git-ignored via the repo's `*.local` rule) and fill in:

```
VITE_SUPABASE_URL=https://your-project-ref.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=your-anon-public-key
```

Restart the dev server after changing env vars.

## 4. Run the database migration

Option A — Supabase Dashboard (simplest):

1. **SQL Editor → New query**.
2. Paste the contents of `supabase/migrations/0001_init.sql`.
3. Run it.

Option B — Supabase CLI:

```
npm install -g supabase
supabase login
supabase link --project-ref your-project-ref
supabase db push
```

This creates every table (`profiles`, `workspaces`, `workspace_members`, `clients`, `projects`, `rooms`, `requirements`, `catalogue_items`, `room_items`, `quotations`, `quotation_items`, `canvas_documents`, `site_photos`, `drive_references`, `local_references`), the `handle_new_user()` signup trigger, every RLS policy, and the `site-photos` Storage bucket + its policies — all in one file.

## 5. Confirm the Storage bucket

The migration already creates a **private** `site-photos` bucket via `insert into storage.buckets`. Confirm it under **Storage** in the dashboard: bucket `site-photos` should show as private (no public toggle enabled). Objects are stored at `<workspace_id>/<project_id>/<filename>` and are only ever accessed through short-lived signed URLs generated by the app — there is no public URL for any photo.

## 6. Configure email templates (recommended)

Under **Authentication → Email Templates**, the default "Confirm signup" and "Reset password" templates work out of the box. For the reset-password flow to land users on the right page, check **Authentication → URL Configuration** and make sure your app's origin (e.g. `http://localhost:5173` for local dev, or your production domain) is in the **Redirect URLs** allow list — the app requests a redirect to `<origin>/reset-password`.

## 7. Test authentication

1. `npm run dev`, open the app — it should redirect to `/login` once `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` are set (local-only mode turns off).
2. **Create one** → sign up with a real email you can access (Supabase sends a confirmation email by default — you can disable "Confirm email" under **Authentication → Providers → Email** for faster local testing).
3. Confirm the email, then sign in.
4. Check **Table Editor → workspaces / workspace_members / profiles** — signing up should have created exactly one workspace (owned by that user) and one membership row, via the `handle_new_user()` trigger. This is the "default workspace per account" requirement.
5. Sign out (Sidebar → account menu → Sign out) and confirm you're returned to local-only-looking behavior with no cloud data visible — this is expected: signing out never deletes cloud data, it just stops showing it locally.
6. Sign back in — the same workspace loads again.
7. **Forgot password**: request a reset link, follow it, set a new password, sign in with the new password.

## 8. Test Row Level Security

RLS is what actually enforces workspace isolation — never rely on the frontend for this. To verify it directly:

1. Create a **second** account (different email) via Sign up.
2. Add a project/client under Account A.
3. In the Supabase **SQL Editor**, run a query as an authenticated user (via `supabase.auth` in the browser console with Account B's session, or the dashboard's "Run as user" feature if available) attempting to `select * from projects where workspace_id = '<Account A's workspace id>'` — it should return zero rows for Account B.
4. In the app itself: sign in as Account B and confirm Account A's clients/projects/rooms/quotations/Canvas/Site Photos never appear.
5. Try a direct REST call with Account B's access token against Account A's workspace_id (e.g. via `curl` to `https://<project>.supabase.co/rest/v1/projects?workspace_id=eq.<A's id>` with Account B's `Authorization: Bearer` header) — it must return an empty array, proving enforcement happens at the database level, not just because the UI doesn't ask for it.

## 9. Test the local-data migration flow

1. Before ever signing in, use the app locally for a bit (add a client, draw something in Canvas, add a Site Photo) — or just use it as-is with the shipped sample data.
2. Sign up for a new cloud account.
3. You should see an **"Existing AURA data found"** prompt listing what would be synced. Choosing **Sync to cloud** pushes it (uploading Site Photos to Storage, generating fresh cloud IDs, remapping every cross-reference); choosing **Start fresh instead** leaves your cloud workspace empty and your local data untouched either way.
4. Reload the page — your data (migrated or not) should still be there, now loaded from the cloud.

## 10. Run the application locally

```
npm install
npm run dev
```

Without `.env.local` configured: local-only mode, exactly like the app worked before this milestone.
With it configured: the full auth + cloud sync flow above.

## Known limitations (see the completion report for the full list)

- Site Photo / local-reference signed URLs are valid for 1 hour; a session left open past that will need a reload to refresh a broken thumbnail (no automatic re-signing is implemented yet).
- Real-time collaborative editing is explicitly out of scope for this milestone (per spec) and is not implemented.
- Google Drive OAuth/Picker itself is unrelated to Supabase and was already documented as its own manual setup step (`.env.example`, `VITE_GOOGLE_CLIENT_ID`/`VITE_GOOGLE_API_KEY`) in the prior Project Media milestone.
